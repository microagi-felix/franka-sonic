## 2. Work packages

### WP 3.1 — token labels (run folder `…_label_tokens`)

`harness/lane_b/label_tokens.py`: run P2's **encoder ONNX** in robot-motion
mode over each demo episode's joint trajectory → `token (T,64)` per frame at
**50 Hz** (the dataset rate; nearest-neighbour if the encoder's own cadence
differs). Offline labelling has the future window the encoder needs — that is
why this is done offline and it is the one deviation from NVIDIA's live-token
recipe. The B-oracle (WP 3.5) is the check that these offline labels are
executable.

Assert: `|token| <= 1.25` (the FSQ grid bound) on the labels themselves; if
labels exceed it, the encoder or the input ordering is wrong.

### WP 3.2 — dataset variant

Same frames, same observations, second action table:

- `action = [motion_token 64 | left_grip 1 | right_grip 1]`, **ABSOLUTE /
  NON_EEF**, `delta_indices = range(40)` (horizon 40)
- state, video and language keys identical to lane A's dataset
- output `<run>/out/gr00t_v2_sonic/` with `meta/modality.json` — this is what
  the gate reads
- modality config: `harness/lane_b/modality_config_dual_fr3_sonic.py`,
  registered under `EmbodimentTag.NEW_EMBODIMENT`, mirroring NVIDIA's
  `unitree_g1_sonic` field-for-field

### WP 3.3 — fine-tune (run folder `…_finetune`, 2 GPUs)

**Exactly P1's command**, only `--dataset-path` and `--modality-config-path`
change:

```
~/Isaac-GR00T/.venv/bin/python -m gr00t.experiment.launch_finetune \
    --base-model-path nvidia/GR00T-N1.7-3B \
    --dataset-path <run-label>/out/gr00t_v2_sonic \
    --embodiment-tag NEW_EMBODIMENT \
    --modality-config-path harness/lane_b/modality_config_dual_fr3_sonic.py \
    --num-gpus 2 --max-steps 2000 --save-steps 500 --global-batch-size 32 \
    --color-jitter-params brightness 0.3 contrast 0.4 saturation 0.5 hue 0.08 \
    --dataloader-num-workers 4 \
    --output-dir <run>/out/checkpoints
```

If P1 deviated (e.g. 1 GPU instead of 2), **match P1's actual command**, not
this listing, and say so in STATUS.md. Lanes trained differently cannot be
compared — that is the whole point of the bake-off.

### WP 3.4 — policy server with the decoder inside (run folder `…_eval`)

`harness/lane_b/serve_gr00t_sonic_joint.py`: GR00T → 40-step token chunk →
**decoder ONNX inside the server** at 50 Hz → `[Lq7, Lg, Rq7, Rg]`. The server
presents the identical contract to the sim as lane A's, so the same client,
binding, rubric and rate are used — the sim side must be literally identical.

- clip `|t| <= 1.25` before the decoder
- the decoder keeps its own proprio history from the streamed state
  (`[token, base_ang_vel, joint_pos_rel, joint_vel, last_actions, gravity]`;
  fixed base → `base_ang_vel = 0`, gravity constant)
- self-encode a "hold" token from the ready pose and feed that on resets (the
  shipped-token trap: a zero token is not a hold)
- replan at 2.5 Hz (`--replan-every 20` at `--rate 50`)

Then:

```
PYTHONUSERBASE=~/env/pyuser-fr3 /isaac-sim/python.sh -m evaluation.eval \
    --run-folder <run>/out/eval --client <the same joint client as P1> \
    --host 127.0.0.1 --port <port> --embodiment franka_dual \
    --rate 50 --replan-every 20 --rollouts 20 --max-steps <same as P1> \
    --no-splat --headless
```

The gate wants **≥ 20 episodes** in `out/eval/eval_results.csv`. Use the same
seeds as P1's eval if the harness lets you — same episodes make the comparison
tighter.

### WP 3.5 — B-oracle replay (run folder `…_oracle_b`)

Stream the encoder-labelled token sequence of each recorded episode through the
decoder with **no VLA in the loop**, through the same eval path, same seeds.
This is lane B's ceiling: if it is low, the controller lost the comparison, not
the VLA — and that is the headline finding for P4. Output:
`out/eval/eval_results.csv` in that run folder.
