### WP 9.0 — parameterise the fine-tune (harness change, do it first)
`_finetune_cmd` hard-codes `--max-steps 2000 --save-steps 500
--save-total-limit 5`. Add CLI flags **`--train-steps` (default 2000),
`--save-steps` (default 500), `--save-total-limit` (default 5)** — note
`--max-steps` already means the *evaluation horizon* in this CLI, so do not
reuse that name. Every checkpoint must be kept (HARD RULE 1): with 20 000 steps

lanes stay comparable.

### WP 9.1 — two fine-tunes, in parallel, 3 GPUs each
Claim 3 GPUs per lane through the allocator and leave **2 devices free for
screening**. Smoke-test the 3-rank NCCL with a 200-step run before committing;
if it faults, fall back to 2 GPUs per lane (20 000 steps ≈ 7.5 h) and record
the fallback.

```
python3 harness/bakeoff.py run lane_a finetune --gpus 3 --dataset <P7 dataset run> \
    --train-steps 20000 --save-steps 2500 --save-total-limit 12
python3 harness/bakeoff.py run lane_b finetune --gpus 3 --dataset <P8 label_tokens run> \
    --train-steps 20000 --save-steps 2500 --save-total-limit 12
```

Machine-diff the two `cmd.sh` files token-wise before you let them run: exactly
three tokens may differ (`--dataset-path`, `--modality-config-path`,
`--output-dir`). Record the diff in STATUS. Expect ~5 h each at 3 GPUs.

### WP 9.2 — screen every checkpoint (20 rollouts), on the 2 spare GPUs
As each `checkpoint-<n>` appears, evaluate it: lane A with
`bakeoff run lane_a eval --checkpoint <ckpt> --rollouts 20`, lane B with the
same plus `--onnx <P8 export run>` (verify in the server log that the **P8**
decoder loaded, as P6 did). Same binding, seeds, rate, replan and horizon as
round 1 — nothing about the evaluation changes between lanes or between rounds.

If screening falls more than two checkpoints behind training, skip to the
newest checkpoint and record the skip; never let screening delay training.

Keep the series in STATUS as it grows, one line per screened checkpoint:
`lane, step, success/20, mean progress, milestone rates`.

### WP 9.3 — the stopping rule (apply it, do not improvise)
Per lane, in checkpoint order, best = highest success count, ties broken by
higher mean progress, further ties by the **earlier** checkpoint:

- From the 4th screened checkpoint onward, stop that lane's trainer when **two
  consecutive screened checkpoints both fail to beat the lane's best**.
- Stop at 20 000 steps regardless.
- Stop a lane early on a hard failure (loss NaN, trainer death) and say so.

Stop a trainer by its recorded pgid (SIGTERM, then SIGKILL the python by pid,
verify with `ps`). Then write the winners as two literal lines, one per lane,
in exactly this form so the gate can read them:

```
P9 BEST lane_a=<absolute path to the chosen checkpoint dir>
P9 BEST lane_b=<absolute path to the chosen checkpoint dir>
```

### WP 9.4 — record
One STATUS line per lane with the full screening series, the chosen checkpoint,
why the rule chose it, GPU-hours and wall-clock. If a lane's series is still
rising when it hits 20 000 steps, say so plainly — that is the headline for the
next round, not something to hide.
