## 1. What is broken (orchestrator's diagnosis from the P2/P3 artifacts)

The B-oracle (encoder-labelled tokens of the 76 demos → decoder → sim, no VLA)
scores **0/20** while the A-oracle scores 20/20. The decoder tracks hand
positions to ~5 cm but not joints: mean joint error 0.66 rad on replay,
per joint L_j7 2.72 (wrapped by ~π), R_j6 1.18, L_j3 1.00, L_j1 0.96,
L_j5 0.77, R_j7 0.74, elbows fine (0.05–0.11). It plateaued from iteration
~1500 of 2300–3500. Why:

- **The reward cannot see the wrist roll or the null space.** The reward
  points are the flanges (`link7 + 0.107 m along z`), i.e. ON the joint-7
  axis, so joint 7 is invisible to the position kernels; link2/link4 origins
  sit on/near the joint-1/joint-3 axes. The body-orientation slot
  (`tracking_relative_body_ori_weighted`) was spare (zero weight) and P2's
  jp2 variant re-used it for a joint term, so orientation tracking is off.
- **The jp2 joint term is too blunt**: `exp(−mean_j Δq_j² / 1.0²)` — one
  wrapped joint (Δ ≈ 3 rad) saturates the mean, the wide kernel gives almost
  no gradient near zero, and weight 2 vs the saturated body terms is small.
- **The information is in the token**: the g1 encoder inputs
  (`command_multi_future_nonflat`, 10 future frames × [7 bodies × (pos 3 +
  ori 6 + lin vel 3 + ang vel 3) + joint pos 14 + joint vel 14] + anchor ori
  6 = 1390 (+1 encoder index = 1391)) include the reference joint positions
  and velocities, and the g1_recon aux loss reconstructs them. So this is a
  reward/training problem, not a token-capacity problem. Verify this (WP 5.1),
  do not assume it.
- Reachability is fine: action = default + 0.25 × a, clip 20 → ±5 rad; FR3
  joint 7 range ±3.0 (soft factor 0.95). Verify (WP 5.1).

### WP 5.0 — launch the retrain FIRST (variant `sonic_dual_fr3_jp3`)

Create `harness/lane_b/sonic_dual_fr3_jp3.yaml` (defaults: `sonic_dual_fr3`,
`_self_`) and extend `harness/lane_b/sonic_rewards.py`; install the yaml the
way `install_gear_sonic.sh` installs the others (canonical copy in this repo,
installed copy under `~/GR00T-WholeBodyControl/gear_sonic/config/exp/`; no
commits in upstream). Changes, all of them:

1. **Joint-space tracking, per-joint kernel mean at two scales**
   (`sonic_rewards:tracking_joint_space`):
   `0.5 · mean_j exp(−Δq_j²/0.5²) + 0.5 · mean_j exp(−Δq_j²/0.15²)`,
   Δq = q − q_ref from the motion command (IsaacLab joint order, exactly as
   `tracking_joint_pos_error` does it). Per-joint mean, NOT exp of the mean
   square — one wrapped joint must not zero the whole term. **weight 4.0.**
2. **Joint-velocity tracking** (`sonic_rewards:tracking_joint_vel`):
   `exp(−mean_j (q̇_j − q̇_ref_j)² / 2.0²)`, reference velocities from the
   command term (the motion lib carries finite-difference joint velocities).
   **weight 1.0.**
3. **Body orientation tracking ON**: restore `tracking_relative_body_ori_weighted`
   to its upstream function with a non-zero weight (1.0) over the 7 tracked
   bodies (or at least both link7s), so the wrist orientation is rewarded.
4. **Reward points off the joint-7 axis**: per hand add two extra reward
   points offset ±0.05 m in the flange x direction (6 points total) so the
   position kernels also see the wrist roll. Keep the `body_names` list and
   the encoder inputs unchanged. If the encoder input width at export (WP 5.2)
   differs from 1391, revert THIS change only and relaunch.
5. Mount the new terms on slots RewardsCfg already has (it is built as
   `RewardsCfg(**dict)`, unknown names raise): the nulled `feet_acc` and
   `undesired_contacts` slots are the obvious hosts (`_target_:
   isaaclab.managers.RewardTermCfg`, `func: sonic_rewards:<name>`,
   `params: {command_name: motion, ...}`). If a slot cannot host a custom
   term, use any other zero-weight slot and say which in STATUS.
6. Everything else stays at P2's values (`sonic_dual_fr3.yaml`: PD gains,
   action scale 0.25, no self-collision, terminations, events, PPO config).
